### 一、Redis + “Session”(非 JWT) 维持用户登录状态
1. 短信登录
采用 `string` 类型存储
- `key` 是“前缀 + 手机号”，`value` 是验证码

2. 维护用户登录状态
采用 `hash` 类型存储
- `key` 是“前缀 + UUID”，`field-value` 用于存储用户相关的信息
    - 这里的 UUID，用来作为用户登录标识，实际上就是 SessionID 的变种
    - 相较于 JWT，这种方式把用户信息全部存储到 Redis 当中（JWT 只需要在 Redis 存储 `(jti,userId)`）

### 二、Redis 作为缓存

1. 商铺信息缓存
- Cache Aside ——旁路缓存
- 设置超时剔除(TTL)

商铺信息更新，造成的 **一致性问题** 解决办法：确保最终一致性（而非强一致性）
- 缓存数据设置 TTL ，并且在 update 时，先写 DB 再删缓存
    - 对非事务资源（布隆过滤器、Redis、Caffeine 等），使用 `afterCommit` 事务同步钩子，防止幽灵信息
    - 此类数据突发情况造成的短时间的脏读（TTL 会过期），不保证突发情况的一致性
- MQ + Outbox（或者监听 Mysql binlog）

#### 2.1 站在 Redis 角度，缓存三大问题与解决办法：
1. 缓存穿透 
- 布隆过滤器拦截大部分 DB 查询不到的访问
    - RedissionBoolom （Java 引入依赖）
    - 程序首次启动时灌数据到 Redis
    - 查询先经过布隆过滤器，更新也需同步更新布隆过滤器
- 缓存空值作为兜底
    - 将空值缓存为 `"NULL"`
    - Redis 查出 value 为 `"NULL"`，直接返回

2. 缓存雪崩
- 真实 TTL + 随机抖动（抖动范围 ≈ TTL 的 10%）

3. 缓存击穿
- 逻辑过期方案抵御大部分情况
- 互斥锁（依赖 Redission）方案作为兜底

另外，在系统 **整体** 性能与可靠性的层面，引入：
- Caffeine 实现多级缓存
- Sentinal 降级限流策略
- Redis 集群（集群没做具体实现）

#### 2.2 站在现实角度，问题归纳为 `api 读写` 两个维度
缓存击穿是在热点 Key（高并发）场景下才会出现的；

解决缓存击穿，从性能角度出发，需要使用逻辑过期；

使用逻辑过期，就不会面临缓存穿透+缓存雪崩问题
- 换句话说：
    - 热点 Key 问题(比如公共数据，商品库存) -> 只需要解决缓存击穿
        - Key 数量少，并发量大
    - 普通 Key 问题(比如用户数据) -> 只需要解决缓存穿透 + 缓存雪崩
        - Key 数量多，并发量小



综上，可以引申出第一个分类维度（指导 **api 读** 的设计）：并发量(cold/hot)维度

普通 Key(低并发)：物理过期+  布隆过滤器+缓存空(防穿透)+  Caffeine+10% TTL 抖动(防雪崩) 
- 同步重建缓存，没有互斥锁，重建缓存时会有多次 DB 访问，多次 Redis set

热点 Key(高并发)：逻辑过期+Caffeine(防击穿)+  Redis上实现悲观写锁(防多个重建缓存线程把 DB 打爆)
- 异步重建缓存，“快返回旧数据”
- 加互斥锁必须异步，因为同步加互斥锁引发线程阻塞，会迅速把线程池耗光



第二个分类维度（指导 **api 写** 的设计）：价值(soft/hard)维度

低价值 Key(允许缓存删除意外丢了或脏读，等到 TTL 来兜底)：affterCommit

高价值 Key(删缓存是一个必须最终发生的事实)：
- 热+高价值 Key，采用后端解决办法（超脱缓存概念）：
    - 监听 Outbox-DB 落盘或监听 Mysql Binlog + Redis 作为状态机
- 普通+高价值 Key，采用前端解决办法（作为缓存，允许短暂脏读，因为正常发生概率小，一旦出事大概率是用户做坏事）：
    - 让前端暂存“刚发生的事实”绕过缓存系统(比如支付宝的用户余额)
    - 设置较短 TTL


从而可以将 `api 读写` 两个维度结合，分为四类问题：
- 普通_低价值 Key
- 普通_高价值 Key（用户余额）
    - 账本型只读投影
    - 并发强度不高，理论上用户在一个前端页面里操作就不会出问题；出问题大概率是用户多开或者使用脚本的锅
- 热点_低价值 Key（排行榜）
- 热点_高价值 Key（商品库存、商品价格、秒杀商品信息）
    - 业务状态型权威缓存
    - 实际上作为状态机，已经超脱传统的“缓存”概念
    - 需要开启 AOF + RDB 进行持久化

值得注意的是，不论 `api` 是读还是写，都会对 Redis 进行写
- 查询数据时有两种情况：缓存有->查缓存，缓存没有->查DB->写缓存(缓存重建)
- 更新/新增/删除数据时：删除缓存

最后，设计并实现了 CacheClient，封装上述四类问题的处理方法
- `queryColdSoftWithBloom`：普通低价值 key 带布隆查询（长 TTL）
- `queryColdHardWithBloom`：普通高价值 key 带布隆查询（短 TTL）

- `queryHotSoft`：热点低价值 key 查询（Redis 作缓存）
- `queryHotHard`：热点高价值 key 查询（Redis 作状态机）

### 三、Redis 作为（计数型）状态机
新建 RedisIdWorker.java 生成全局唯一 ID 
- ID = 时间戳 + 当天自增序列

典型结构
```text 
1 位符号位 + 31 位时间戳 + 32 位序列号 = 64 位 long
```
- 符号位：1bit，永远为 0
- 时间戳：秒级，可以使用 69 年（用相对时间计算）
- 序列号：Redis INCR 生成。支持每秒产生 2^32 个不同 ID（每天重置）


#### 下单场景两大问题与解决方案
1. 计数资源竞争问题（超卖问题）

超卖 = 库存一致性问题

解决方案——Redis 扣库存 + 异步落库：
```bash 
Redis 扣库存（原子）
↓
消息队列 / Stream
↓
DB 最终一致
```

2. 唯一性问题（一人一单问题）

一人一单 = 用户幂等 + 并发唯一性问题
- Redis 原子校验 + DB 唯一索引兜底
    - 将 `user_id + voucher_id`，建立为 `tb_user_voucher` 中的唯一索引
```sql 
ALTER TABLE voucher_order
ADD UNIQUE KEY tb_user_voucher (user_id, voucher_id);
```

#### 完整秒杀链路
```text 
请求进来
↓
Redis Lua（原子执行）
  ├─ 库存 > 0？
  ├─ 是否已下单？
  ├─ 扣库存
  ├─ 记录用户
  └─ XADD Stream（写订单消息）
↓
立即返回成功
↓
Stream Consumer 异步消费
↓
DB 落单（唯一索引兜底）
```
- 采用 Redis Stream 作为秒杀消息队列
- Redis 开启 AOF（everysec） + RDB（兜底） 进行持久化
- Redis 中，库存使用 String，用户下单记录使用 Set 存储

生产者秒杀 Lua 脚本三个输入
- userId：用户 id，上下文获取
- voucherId：优惠券 id，添加优惠券时生成（雪花或自增）
- orderedId：订单 id，RedisIdWorker 生成

生产者秒杀 Lua 脚本输出状态码约定
- 0：成功
- 1：库存不足 
- 2：重复下单
